# 代码导读：这套 RAG 到底怎么跑的（改造后可自查版）

> 目的：让你**不依赖 AI、不用看完全部代码**，也能把「一个问题从进来到出去」讲清楚，
> 并且能自己动手改一个小功能。文中 `文件:行号` 都指向当前仓库代码。

---

## 0. 一句话版本

把 12 份公司制度切成小段存进两个索引（向量库 + 关键词索引），用户提问时两路各找 10 段，
用 RRF 把两路排名融合成一份候选，再让 reranker 精排取前 3 段，塞进 prompt 交给 DeepSeek
生成答案，答案里带「文件 · 第X条」的出处。

## 1. 全链路总图

```
                    ┌──────────────────── 建库（启动时一次） ────────────────────┐
 知识库/*.txt|pdf|docx                                                                
        │                                                                             
        ▼  smart_loader.load_file()            按扩展名解析；坏文件报错不吞          
   Document(page_content, metadata.source)                                            
        │                                                                             
        ▼  clean_pipeline.clean_document()     统一换行/去全角空格/去重复行           
        │                                                                             
        ▼  RecursiveCharacterTextSplitter      200 字/块，重叠 20，按句号问号切        
   chunks（当前 12 份文档 → 47 块，约 4 块/份）                                                                
        │                                                                             
        ├──► 生成 chunk_id = d<文档号>_c<块号>，写入 metadata["chunk_id"]               
        ├──► Chroma.from_documents(ids=chunk_id)  → 向量库（进程内，重启重建）         
        └──► BM25Okapi(jieba 分词后的 chunk)      → 关键词索引                        
                                                                                       
                    └──────────────────────────────────────────────────────────────┘

                    ┌──────────────────── 问答（每个请求） ──────────────────────┐
 用户问题 "报销超过5000元谁审批"                                                        
        │                                                                             
        ▼  HybridRetriever.retrieve_meta(q, top_k=10)                                 
        │     ├─ _dense_ids()：Chroma 语义检索 top-10                                 
        │     ├─ _bm25_ids()：BM25 关键词检索 top-10                                  
        │     └─ _rrf_ids()：两路排名做 RRF 融合 → 10 条候选（ChunkMeta）             
        ▼  rerank.rerank_objects(q, 候选, top_n=3)   bge-reranker-v2-m3 逐条打分       
   3 条 ChunkMeta（最相关的 3 段，带 citation）                                         
        ▼  rag_qa.format_context() + build_prompt()   拼「[来源：文件 · 第X条] 正文」   
   prompt（含防幻觉要求：先给依据、再给结论、找不到就说不知道）                         
        ▼  ChatOpenAI(deepseek-chat, temperature=0).invoke(prompt)                    
   answer + sources[{chunk_id, source, text}]                                          
                    └──────────────────────────────────────────────────────────────┘
```

## 2. 建库阶段：文档怎么变成可检索的块

| 步骤 | 代码位置 | 关键点 |
|---|---|---|
| 解析 | `smart_loader.py:48` `load_file()` | 按扩展名分派：txt/md（UTF-8→GB18030 回退）、pdf（PyPDFLoader，带页码）、docx（段落+表格） |
| 容错 | `smart_loader.py:107` `load_documents_with_report()` | 单文件失败只记 `{file, error}`，不炸整次构建；全部失败才抛 |
| 清洗 | `clean_pipeline.py:51` `clean_document()` | `clean_text` + `dedupe_lines`：统一换行、去零宽字符、压缩空行、删完全重复行 |
| 切块 | `hybrid_retriever.py:176` `build_hybrid()` | `RecursiveCharacterTextSplitter`，分隔符优先级 `\n\n → \n → 。！？；，`，`chunk_size=200`、`overlap=20` |
| 编号 | 同上 | `chunk_id = d01_c03`；**同时写进 Chroma 的 id 和 metadata**，检索后能还原出完整元数据 |
| 建索引 | 同上 | 向量：`Chroma.from_documents(ids=chunk_ids)`；关键词：`BM25Okapi([jieba.lcut(text)])` |

**为什么 chunk 是 200 字**：块越大召回越宽、排序越差；块越小定位准但上下文不够。之前用
`eval_chunk_experiment.py` 对比过，200 是当前的折中最优，不是拍脑袋。

**为什么不用「文本当 ID」**：制度文件里有重复句子（如"需经部门经理审批"）。用文本当 key 时
两个块会互相覆盖，`id → 文本 → 元数据`的映射就错位了，引用会指错文件。所以有 `chunk_id`。

## 3. 查询阶段：7 步，每一步在哪个函数

1. **接问题**：CLI `rag_qa.py:172 main()` / HTTP `rag_api.py:168 ask()`
2. **检索**：`rag_qa.py:74 retrieve_and_rerank()` → `hybrid_retriever.py:150 retrieve_meta()`
3. **两路召回**：`hybrid_retriever.py:118 _dense_ids()` 与 `:122 _bm25_ids()`
4. **RRF 融合**：`hybrid_retriever.py:133 _rrf_ids()`
5. **精排**：`rerank.py:97 rerank_objects()` → `:65 score_pairs()`
6. **拼 prompt**：`rag_qa.py:61 format_context()` + `:70 build_prompt()`
7. **生成**：`rag_qa.py:95 answer()` 里 `llm.invoke(prompt)`

### 3.1 RRF 到底在算什么（手工算一遍就懂了）

公式：`score(d) = 1/(k + 向量排名) + 1/(k + BM25排名)`，`k=60`。

假设问"5000元审批"：

| 块 | 向量排名 | BM25 排名 | RRF 分数 | 结论 |
|---|---|---|---|---|
| A（报销审批权限） | 2 | 1 | 1/62 + 1/61 = 0.03253 | 第 1 |
| B（考勤时间） | 1 | 无 | 1/61 = 0.01639 | 第 2 |
| C（打款时限） | 3 | 4 | 1/63 + 1/64 = 0.03150 | 第 3（保留） |

**要点**：RRF 只用「排名」不用「分数」，所以不需要把向量的余弦相似度和 BM25 的分数量纲对齐；
两路都靠前的块会被顶上去（A 的向量排名不如 B，但两路都命中，最终反超 B）。

### 3.2 为什么还要 reranker（以及它的天花板）

- 向量/BM25 是**粗排**：把 47 个块砍到 10 个候选，看重的是"别漏"。
- reranker 是 **cross-encoder**：把 `(问题, 块)` 一起喂进模型逐对打分，看重的是"排得准"。
- **关键认知**：rerank 只在候选集内部重排，**不可能提高 Recall@10**——10 条候选里没有的东西，
  怎么排都出不来。所以它的收益体现在 **R@1 / R@3 / MRR**，天花板由召回池决定
  （`eval_recall_pool.py` 实测：池子 5→10，池内命中 86%→95.3%）。
- 降级：模型不可用时 `score_pairs()` 返回 `None`，`rerank_objects()` 返回原顺序并标
  `fallback=True`，主流程照跑（`rerank.py:65-95`）。

### 3.3 服务层（`rag_api.py`）——它只做三件事

1. **检索器懒加载**：`get_retriever()`（`:69`）第一次请求才构建索引（40-60 秒），之后复用；
   构建失败抛 `503`，不缓存半成品。
2. **文档变更后重建**：`rebuild_retriever()`（`:90`）在锁内构建新检索器，**构建成功才替换引用**
   （`_retriever = new_retriever`）。所以重建期间正在服务的请求仍然用旧索引，不会读到半截状态。
3. **失败回滚**：上传先写临时文件再 `os.replace` 原子落盘；重建失败就删掉新文件（覆盖场景则还原
   `.bak`）；删除会先备份成 `.deleted`，重建失败再 `os.replace` 还原。用户看到的是
   `500 + 中文原因 + "已回滚"`，而不是"文件没了、索引还指着它"。

另外两个入口：`/health`（`:152`，配置问题 + 检索器状态 + chunk 数，用来判断"是不是还没建好"）、
`get_llm()`（`:108`，密钥缺失时抛 `ConfigError` → 接口返回 503 并说明怎么配）。

> 读服务层代码时抓住一条主线：**HTTP 层只管参数校验和错误翻译，检索/生成一律复用 `rag_qa.py`**。
> 如果哪天发现 `rag_api.py` 里冒出检索逻辑，那一定是复制粘贴造成的分叉。

## 4. 评测：怎么证明"真的变好了"

脚本：`eval_v3.py`（100 条核验测试集 `eval_set_v3.json`）

**测试集怎么构造**（这一步决定评测有没有意义）：
6 类共 100 条 —— 普通事实 25 / 条款编号 15 / 数字金额时间 20 / 相似条款辨析 15 /
跨文档 15 / 知识库无答案 10。每条都带 `source`（文件名）、`articles`（条款号）、
`evidence`（原文逐字摘录）。

`verify_eval_set.py` 会做**机器校验**：id 唯一、条款号在原文存在、evidence 能在原文逐字命中
（多段用 `…` 连接）。凭印象编出来的 gold 会在这里被抓出来。

**指标口径**（两条线都要看）：

| 指标 | 定义 | 看什么 |
|---|---|---|
| 文件级 Recall@K | 期望文档出现在 top-K 即算命中 | 有没有"找错文件" |
| 条款级 Recall@K | 文件名对 **且** 条款号有交集 | 定位是否精确到条款 |
| MRR | 第一个命中排名的倒数，取平均 | 排序质量（第 1 位命中=1.0） |
| AllSource@10 | 跨文档题：多个期望文档是否都在 top-10 | 多跳问题能否一次召回 |

**为什么条款级更严格**：文件级只要文件名对了就算过，但同一个文件里第 3 条和第 8 条说的不是
一件事。只看文件级会高估（`eval_gold_article.py` 实测：文件级与条款级差 15.5pp 假阳性）。

**怎么判断"提升是真的"**：同一份测试集、同一次构建、只改一个变量，看 MRR 和 R@1 是否同向变化；
不要只看单条 case 的故事——单条变好可能只是运气。

## 5. 想自己改一个功能？从这三个开始（都有明确验收标准）

**练习 1｜改 prompt 的引用格式**
- 改 `rag_qa.py:32 PROMPT_TEMPLATE`，要求模型输出 `【出处】…`。
- 验收：`python -m pytest` 全绿；跑一次 `python rag_qa.py` 提问，答案里出现新格式。

**练习 2｜把进 prompt 的条数从 3 改成 5**
- 改 `.env` 的 `RERANK_TOP_N=5`（不用改代码——这就是配置化的意义）。
- 验收：`python eval_v3.py --limit 20` 里 C 方案不变（评测取 top-10 不截断），
  但问答耗时上升；能解释"为什么条数变多不一定更准"（噪声进 prompt）。

**练习 3｜给 /documents 增加一个字段**
- 在 `rag_api.py:193 list_documents()` 的 items 里加 `"ext": p.suffix`。
- 验收：先在 `tests/test_api.py` 里加断言，再改实现，跑 `python -m pytest tests/test_api.py`。

## 7. 常见报错 → 原因 → 修法

| 现象 | 原因 | 修法 |
|---|---|---|
| `ConfigError: 配置有 N 处问题` | 模型路径/密钥/知识库目录不对 | 按报错逐条改 `.env`；`python config.py` 可单独自检 |
| 启动卡十几分钟不动 | 本地模型目录被 sentence-transformers 拿去联网校验 | 已在 `config.py:191 prepare_local_model_env()` 里自动设 `HF_HUB_OFFLINE=1` |
| `reranker 模型加载失败` | 路径错/缺 `sentence-transformers` | 改 `RERANK_MODEL`；或 `USE_RERANK=0` 直接关掉精排 |
| 上传后检索不到新内容 | 重建失败被回滚 | 看响应里的 `file_errors`（哪个文件没解析成功、为什么） |
| 答案里条款号指错文件 | 老代码拿文本当 ID 导致映射错位 | 本仓库已改为 `chunk_id`，若见到说明跑了旧脚本 |
| `pytest` 报 PermissionError（临时目录） | 受限环境无法在系统 TEMP 建目录 | 已用 `tests/conftest.py` 自定义 `tmp_path` 落在仓库 `.tmp/` |
