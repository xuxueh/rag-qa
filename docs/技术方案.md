# 核心技术方案与取舍

> 原则：**每一层都写清"为什么这么选"和"证据在哪"**。没有证据的优化一律不进主干
> （Multi-Query 就是被评测否掉后保留在实验脚本里的例子）。

---

## 1. 问题定义与边界

- 场景：企业制度问答。用户问的是**有唯一正确答案的事实型条款**（几天、多少钱、谁审批、第几条）。
- 首要风险：**编造**（幻觉）。制度类问答里，一个错误数字比"答不出"危害大得多。
- 次要风险：**定位不到条款**（检索错文件/错条款），会让答案"看起来对，出处是错的"。
- 因此方案排序是：**可溯源 > 拒答 > 召回质量 > 速度**。

知识库现状：12 份制度文档，清洗切块后约 47 个 chunk（`eval_results_v3.json → meta.chunks`）。
规模很小，这一点决定了后面若干取舍（见第 7 节）。

---

## 2. 切块（chunking）

| 决策 | 取值 | 依据 |
|---|---|---|
| 块大小 | 200 字 | `eval_chunk_experiment.py` 对比（v2 50 条集）：块越大召回越宽但排序变差，200 是折中最优 |
| 重叠 | 20 字 | 防止条款被切断后关键词落在边界 |
| 分隔符优先级 | `\n\n → \n → 。！？；，` | 中文制度以"第X条：…。"为结构单元，优先在句子边界切，避免半句话 |

**代价**：一个长条款可能被切成两块，条款号只落在第一块上 → 条款级评测会低估（见第 6 节）。

---

## 3. 混合检索：向量 + BM25 + RRF

**为什么不是纯向量**：制度问题常带强字面信号（"5000 元""第 3 条""90 天"）。向量对这类
"数字/编号"不敏感——语义上"金额超过五千需要谁批"和"单笔金额超过 5000 元的需总经理审批"
很近，但换个数字（500 vs 5000）向量几乎分不开，BM25 能。

**为什么用 RRF 而不是加权分数**：两路分数不可比（余弦相似度 vs BM25 的负数/无上界分数），
归一化会引入超参。RRF 只用**排名**：

```
score(d) = Σ_route 1 / (k + rank_route(d))      k=60
```

**为什么双路各取 Top-K 再融合**（而不是 BM25 全库参与）：
- `eval_rrf_candidates.py` / `eval_rerank_pairwise.py`（v2）：双路 Top-K 比全库融合
  **rerank 链路 R@1 +9.3pp、MRR +0.078**。
- 机理：全库参与会让"排名很靠后但仍参与融合"的块稀释高质候选。

**已知副作用**：RRF 会把"某一路排名极高"的正确项挤出候选（跨文档题最明显）→ 靠 rerank 弥补
（v2 实测跨文档 R@1 +28.5pp）。这就是为什么 rerank 在本项目里不是可选项。

## 4. 精排（rerank）

- 模型：`BAAI/bge-reranker-v2-m3`（本地，cross-encoder，`(查询, 块)` 逐对打分）。
- 位置：召回 10 → 精排取 3 进 prompt。
- **天花板意识**：rerank 只在候选集内重排，**不会提高 Recall@10**；收益体现在 R@1/R@3/MRR。
  召回池决定上限（`eval_recall_pool.py`：池 5→10，池内命中 86%→95.3%）。
- **成本**：CPU 上 10 对约 5-6 秒/次（本轮 100 条实测），是当前问答延迟的主要来源。
  这是明确的取舍：宁可慢 5 秒，也不要引错条款。可优化方向见规划文档。
- 降级：模型缺失/推理异常 → 返回原顺序 + `fallback=True`，服务不中断。

## 5. 防幻觉与可溯源

1. **prompt 约束**（`rag_qa.py PROMPT_TEMPLATE`）：先给依据（文件 · 第X条）、再给结论、
   不得超出资料范围、逐条核对不遗漏、找不到才说"不知道"。
2. **Citation 贯穿全链路**：`chunk_id` 从建库到答案一直是同一对象（`ChunkMeta`），
   不做"文本→找来源"的反查（反查在重复句子上会错位）。
3. **拒答阈值**（实验性）：用最高精排分做阈值判断，可行性与代价见评测报告的"无答案分析"。
4. **数据层拦截**：`eval_abstention.py`（v2）测过三种 prompt，保守版拒答率 100%、编造 0；
   积极版回答率 97.7%、编造 1 条（边界案例）。当前用积极版，权衡写在 README。

## 6. 评测方法论（怎么避免自欺）

| 做法 | 为什么 |
|---|---|
| 测试集**逐条核验**：source + 条款号 + 原文摘录 | 凭印象编 gold 会让指标失去意义；`verify_eval_set.py` 机器校验 |
| 6 类问题分别统计 | 平均分会掩盖"跨文档全崩"这类结构性问题 |
| 文件级 + 条款级双指标 | 只看文件级会高估 15.5pp 假阳性（v2 `eval_gold_article.py`） |
| 同一次构建内对比 | 不同构建（chunk 参数/文档版本不同）不可比 |
| 检索侧评测不调大模型 | 排除生成噪声、可重复、零 token 成本；生成质量单独用 LLM-as-judge 评 |
| 记录耗时 | 5pp 的检索提升如果换来 10 倍延迟，需要显式权衡 |

**指标定义**：Recall@K = 期望文档出现在 top-K 的比例；MRR = 首个命中排名倒数的均值；
条款级 = 文件名对 **且** 条款号有交集；AllSource@10 = 多文档题的期望文档是否全部进入 top-10。

## 7. 工程取舍（本阶段刻意不做的事）

| 没做 | 原因 | 什么条件下该做 |
|---|---|---|
| Docker / K8s | 当前单机单进程，12 份文档；先保证可靠再谈部署 | 要多实例/多环境一致交付时 |
| 微服务拆分 | 拆分只会增加跨进程调试成本 | 检索与生成需要独立扩缩容时 |
| 独立向量库服务（Milvus/Qdrant） | 50 个 chunk 内存态足够；进程内 Chroma 启动即用 | chunk 数 > 10 万或需持久化共享 |
| 异步任务队列 | 重建 1-2 分钟，同步可接受且状态简单 | 文档量大、重建分钟级以上、要多请求并发写 |
| 缓存 / 限流 | 单用户内部工具 | 对外提供服务时 |
| 增量索引 | 全量重建更简单、不会出现"删了没删干净" | 文档数上千时 |

已做的工程保障：配置集中（`config.py`）、启动自检、日志分级、异常带修复建议、
上传/删除失败回滚、55 个自动化测试、评测集门禁、离线模型加载（避免联网卡死）。
