# 已知问题与规划

> 原则：**问题要有证据**（哪个测试集、哪条 case、多少 ms），规划要有触发条件
> （不是"以后也许可以做"）。

---

## 一、已知问题（按影响排序）

### P1 精排延迟：CPU 上 6.1 s/次
- 证据：`eval_results_v3.json → modes.C_混合+Reranker.latency`：mean 6111 ms、p95 7010 ms；
  混合检索只要 25 ms。端到端问答 5-9 s 里绝大部分是精排。
- 影响：单用户内部工具可接受，多用户/在线场景不可接受。
- 可选修法（按性价比排序）：
  1. 只对混合检索的 Top-5 精排（候选减半，延迟近似减半，R@1 可能掉 1-2pp，需实测）
  2. 精排批量化 + `torch.set_num_threads` 调优 / `torch.inference_mode()`
  3. ONNX Runtime 或 INT8 量化（bge-reranker 有 ONNX 版本）
  4. GPU（最直接，但改变部署成本）

### P2 语料太小，评测接近饱和
- 证据：12 文档 → 47 chunk，Top-10 覆盖 21% 语料；B/C 的 R@10 已是 100%。
- 影响：无法用 R@10 区分"召回好坏"；rerank 收益被小语料放大。
- 修法：扩语料到 ≥ 500 个 chunk（把制度换成完整员工手册/多部门文档），重跑 `eval_v3.py`
  看绝对指标下降多少，再决定是否引入新组件。

### P3 文件级 vs 条款级还有 3.4pp 差距（生产链路）
- 证据：C 方案文件级 R@1 97.8%，条款级 94.4%（`2 条 case` 文件对、条款错）。
- 根因：chunk 按 200 字切，条款号只落在第一块上；同一份文件的相邻条款会被合并。
- 修法：**结构感知切块**——先按「第X条」正则切，再对超长条款二次切分，chunk 元数据保留条款号。
  这是目前最值得做的检索优化（成本低、收益可测）。

### P4 重复条款分散打分
- 证据：`N15「试用期是几个月？」` 在 B 方案排第 4（05 与 09 都写"3 个月"）；
  `S02「不出差时餐饮补贴」` 在 A 方案排第 4（与 06 的出差补贴高度相似）。
- 修法：`also`（多期望文档）已在评测里支持；生产侧可在 prompt 里允许多来源并列，
  或做"文档级聚合分数"（同文件多块命中时加权）。

### P5 无答案边界：限定词不匹配会误判
- 证据：`Y05「国际出差的差旅费报销标准？」` 精排最高分 **0.944**（高于有答案题的最低分 0.223）；
  知识库只有国内标准。阈值 0.21 在这条上失效。
- 修法：① prompt 明确"若资料与问题的范围/对象不符（如国际 vs 国内），也算不知道"；
  ② 加一层"实体/限定词核查"（问题里的关键限定词是否出现在候选文本中）；
  ③ 保留分数阈值作第一道闸门（本测试集 90% 拦截、0 误杀）。

### P6 上传/删除重建期间请求被阻塞
- 现状：重建 1-2 分钟，同步完成；期间其它 `/ask` 用的是旧索引（正确），但上传请求会等很久。
- 修法（触发条件：文档数 > 100 或重建 > 5 分钟）：后台任务 + 任务状态查询，前端轮询。

### P7 索引不持久化
- 现状：`Chroma.from_documents` 是进程内索引，重启后首次提问要重建（约 1 分钟）。
- 修法：`persist_directory` + 文档指纹（mtime+size）判断是否需要重建。

### P8 测试集由开发者自建
- 风险：自己出题自己做，可能系统性避开难点。
- 修法：接真实提问日志（企业里最不缺），按月抽样 30 条替换同类型题目，并保留历史版本以便回归。

### P9 生成侧缺大规模评测
- 现状：本轮只评检索；历史 50 条集做过 LLM-as-judge（20/20 正确）与 Ragas
  （context_precision 1.000 / answer_relevancy 0.955 / faithfulness 0.648）。
- 修法：写 `eval_answers_v3.py`，对 100 条做「引用是否正确 + 答案是否符合 gold + 该拒答时是否拒答」
  三项判定；成本约 100 次调用，可接受。

### P10 未验证项
- `Dockerfile` 未实际构建；`requirements.txt` 本轮已补齐（fastapi/uvicorn/pypdf/python-docx），
  但没在干净环境跑过一次 `pip install -r requirements.txt`。
- 触发条件：要交付他人运行前，必须在干净虚拟环境/容器里验证一次。

## 二、规划（按触发条件推进）

### 短期（不需要新依赖，1-2 天）
1. **结构感知切块**（P3）→ 预期条款级 R@1 +2-3pp，用 `eval_v3.py` 同口径验证
2. **精排候选裁剪实验**（P1）→ 跑 `top-5 vs top-10` 的 R@1 / 延迟曲线，写成一张表
3. **生成侧 100 条评测**（P9）→ 补上"检索好 ≠ 答案对"的最后一块
4. **Docker 验证**（P10）→ 干净环境跑通再写进 README

### 中期（需要改架构）
5. 持久化索引 + 文档指纹（P7）
6. 异步重建 + 任务状态（P6）
7. 文档级分数聚合 + 多来源引用（P4）
8. 拒答双层：分数阈值 + 限定词核查（P5）

### 长期（看使用场景）
9. 多知识库/权限隔离、问答日志与 badcase 回流
10. 监控指标：P95 延迟、拒答率、引用正确率、失败题型分布

### 明确不做的
- 引入 Kubernetes/微服务（单机够用，拆分只会增加调试成本）
- 换成向量数据库服务（50 chunk 用不上）
- 追新框架重写链路（当前链路每一层都有数据支撑，重写等于丢掉基准）

## 三、什么时候可以停止优化 RAG、转向 Agent

对照"实用达标线"自评（**不是行业认证**，只是本阶段的判断）：

| 能力 | 达标标准 | 当前状态 | 判断 |
|---|---|---|---|
| 代码理解 | 能解释核心模块并独立改小功能 | 有 `docs/代码导读.md`（含自查清单、3 个练手任务）；链路 7 步都有函数级定位 | ✅ 有材料，但**要你自己讲一遍才算真会** |
| RAG 原理 | 理解切块/Embedding/向量检索/BM25/RRF/Reranker | 技术方案文档写清了"为什么"；RRF 有手工算例；rerank 天花板有数据 | ✅ |
| 检索评测 | 能建测试集、算并解释 Recall@K / MRR | 100 条核验集 + 门禁脚本 + 三方案对比；能解释文件级 97.8% 与条款级 94.4% 的差 | ✅ |
| 问题排查 | 能定位常见检索/生成错误 | 失败案例已归因到"向量对字面对称不敏感""双文档重复条款分散""限定词不匹配"三类 | ✅ 有 12 个具体 case 可复盘 |
| 工程能力 | 能处理基本异常、配置、日志 | config 集中 + 自检、错误带修法、上传/删除回滚、61 个测试 | ✅ |
| 项目展示 | 别人能照说明跑起来并测试 | README + 架构图 + 技术方案 + 评测报告 + 演示记录 | ⚠️ 差一项：干净环境 / Docker 未验证 |

**结论**：除"独立讲解"和"干净环境验证"两件小事外，当前项目已到**可以停止继续加 RAG 组件**的状态。
再往下加 Multi-Query、HyDE、GraphRAG 之类，收益都会被"语料只有 47 个 chunk"这个天花板吃掉——
**先把语料和评测做大，比换更花的技术更值钱**。

建议的收尾动作（做完就正式转向 Agent）：
1. 他不看 AI，自己讲一遍第 3 节链路（讲不通就去补 `docs/代码导读.md`）
2. 在干净虚拟环境里 `pip install -r requirements.txt` + `python -m pytest` + `python eval_v3.py --no-rerank` 跑通
3. 做一次结构感知切块实验（P3），拿到"改一处、指标动多少"的完整体感

之后 RAG 只在该修 bug 或换语料时回来；主线转 Agent。
